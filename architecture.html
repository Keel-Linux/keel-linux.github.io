Architecture

How far the architecture goes

The architecture the project aims for, in three scenarios. The first is the goal of the first release. The second is decided (decision 0020) and not built. The third is a direction with no design yet.

  1. Keel Linux Standalone Our goal · not yet released
  2. Keel Cloud, three nodes Planned
  3. Separated tiers Future
Scenario 1

Keel Linux Standalone

Our goal · not yet released

This is what Keel Linux is building first. It runs today from source and test images; there is no release for end users yet.

One LXC container or VM runs the whole stack: the application, its database and its files. One instance spec describes it, and Keel keeps the machine and the spec in step.

  • Declared and compared. keel inspect reads the running machine, keel diff shows where it differs from the spec, keel spec apply converges it and is safe to run again.
  • Network changes that undo themselves. VM only · in keel 0.9.0, not yet released On a VM, a changed network must be confirmed with keel network confirm from a new session within 120 seconds, or the previous configuration comes back. A machine reached only over SSH is the case this is for. In an LXC container the host owns the network; keel compares it and does not change it.
  • Not through Webmin. The network is changed in confconsole or at the command line; Webmin shows it read-only (decision 0019).
Scenario 2

Keel Cloud, three nodes

Planned, decision 0020

Three nodes, LXC containers or VMs, two or three of them holding the application: one primary takes the writes, the replicas follow it and stand ready to take over. Keel Cloud is optional: three standalone appliances configured by hand do the same, and Keel Cloud only automates the setup; without it, the public name is moved by hand after a failover.

  • Keel Cloud is optional. keel-cloud adds DNS with a health check, node discovery and WireGuard key exchange. It is in the spirit of TurnKey's HubDNS, which updates a name but checks no health. An API key for it is offered at installation and never required.
  • The election is its own project, keel-quorum. One etcd election for the whole appliance: database, files and web tier are promoted together. Every data node is a voter; the third node may be a voter that holds no data, which is not an appliance and runs only etcd and keel-quorum.
  • Private network. The nodes talk over WireGuard. Its configuration is converged under the same 120 second confirmation window as any network change.
  • Status panel. A read-only screen in confconsole shows one line per node: role, replication lag, last file pull, health, and the elected leader. It changes nothing on the other nodes.
  • What it does not promise. Replication and the file pull are asynchronous, so the last seconds before a failure can be lost. DNS takes one to five minutes to follow a failover, and some resolvers ignore low TTLs. In an LXC container there is no watchdog, so fencing relies on the process demoting itself in time; a VM can have one.

Chosen by the operator when the set is formed

Made once and stored in etcd, so every node reads the same answer. The same choices exist with or without Keel Cloud.

Scenario 3

Separated tiers

Future

The application and the database move to machines of their own. Not designed yet: only the remote database (0013 phase 1) and Galera (0013 phase 4) are planned pieces.

  • A remote database first. An application pointing at a database on another machine is the first piece (decision 0013, phase 1). It is deferred today.
  • Replication, or Galera. Primary and replicas on both engines; Galera gives MariaDB several writers, with a minimum of three nodes.
  • Sharding is possible, not promised. MariaDB has Spider packaged in Debian 13. PostgreSQL has the pieces but no product: Keel configures the role of the node, and the partition scheme stays with whoever designs the system.
