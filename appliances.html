Appliances

Nine appliances, in testing

Every image here is a testing pre-release for Proxmox VE containers. None is a stable release, and none is for production. This page says what each one is, how it was tested, and what the tests do not show.

Test method

How the images were tested

The full test uses 3 containers on real Proxmox nodes: 2 in one site and 1 in another. The database pair sits across the 2 sites.

What the test does

  • It forms a mesh and an etcd of 3 members.
  • It writes to the VIP while a fault happens: a network cut of the primary, or a stop of the holder.
  • It runs once at base and once with netem: 250 ms delay, 25 ms jitter and 1.5 % loss.
  • It counts every acknowledged write and looks for each one on the new primary.
  • It checks that the old primary comes back read-only and does not take writes.

What the numbers say

  • The VIP moved to the other node 17 to 22 s after the fault.
  • The first write was acknowledged 0.3 to 2.7 s after the VIP moved.
  • No acknowledged write was lost in any run listed on this page.
  • These runs are not a proof. They are evidence from a small number of runs.
What the tests do not show

No test cut a whole site. Two of the 3 etcd members sat in the first site, because the third site was offline. The tests cut or stopped one database node. Redis has no failover test. The base images, Core, Web, MariaDB, PostgreSQL and Redis, have no netem run on their current build.

Get an image

Download, check, create the container

The Proxmox template list does not show Keel images yet. Download the file from the release page and copy it to the template storage of the node.

  1. Open the pre-release page of the appliance, from the card above.
  2. Download the .tar.zst, the .sha512 and the .sha512.asc. Signed images have all three.
  3. Check the signature, then the digest.
  4. Copy the .tar.zst to /var/lib/vz/template/cache/ on the Proxmox node.
  5. Create the container.
# example: LNMP 19.0-4. Change the names for another image.
BASE=https://git.pop.coop/Keel-Linux/keel-lnmp/releases/download/testing-19.0-4-20261016
F=debian-13-keel-lnmp_19.0-4_amd64.tar.zst
curl -fLO $BASE/$F -O $BASE/$F.sha512 -O $BASE/$F.sha512.asc
curl -fLO https://archive.keellinux.org/keel-images-keyring.asc

sqv --keyring keel-images-keyring.asc $F.sha512.asc $F.sha512
sha512sum -c $F.sha512

cp $F /var/lib/vz/template/cache/
pct create 200 local:vztmpl/$F --hostname web1 \
  --unprivileged 1 --features nesting=1 \
  --net0 name=eth0,bridge=vmbr0,ip6=2001:db8:1::10/64,gw6=2001:db8:1::1

The signature file holds two signatures: one by the main key and one by the images key. The command uses the images keyring, so sqv prints "Missing key" for the main key. This is expected. If sqv exits 0 and prints the fingerprint E71DB9C3CA6AC18075395CC3ED3A709C4F3E2F3C, the check passed.

An image with no .sha512 file has no signature. Do not use it for anything that matters. Its release page says "NOT SIGNED".

A pair across sites needs 2 nodes of the same appliance and a third etcd member. The cloud page describes the modes. The evidence files list the commands that the tests used.
