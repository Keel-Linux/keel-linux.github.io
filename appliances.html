Appliances

45 appliances for Proxmox VE

The stable channel holds 11 applications, each as a signed LXC template and a signed ISO. Release 2026-11-10 published 8 of them. Release 2026-11-11 added MariaDB, Redis and ntfy. 34 more are in development. Every appliance is a mesh-native Proxmox container that can join a private cloud on day one.

Test method

How the images were tested

Each image passed the commissioning test before it was published (decision 0075). The test installs the image on 2 sites, BR1 and BR2.

What the test does

  • It installs the LXC template on BR1 and on BR2 in 2 ways: answered on the console, and described before the boot.
  • It installs the ISO in a virtual machine on BR1 and on BR2.
  • It installs the modes simple, cloud simple and cloud advanced (decision 0076). The primary is on BR1 and the replica is on BR2.
  • It checks the services, the web addresses and the screens of each node.

What a pass needs

  • A pass is green only if every check of the pass is green.
  • No image is published before every pass of the image is green.
  • Each application of release 2026-11-10 has 8 passes: 6 for the template and 2 for the ISO. Its card gives the count of checks.
  • In release 2026-11-11, MariaDB has the same 8 passes. Redis and ntfy have no cloud mode, so each has 6 passes: 4 for the template and 2 for the ISO.
  • The page of each application has the commissioning table and the screens of each pass.

What the tests do not show

In cloud advanced, the witness was on BR1, so 2 of the 3 etcd members were in one site. The commissioning table gives a count of checks. It does not give failover times or a count of lost writes. The failover tests below give such numbers, but they used earlier builds, not the images of release 2026-11-10.

Get an image

Download, check, create the container

The Templates dialog of the Proxmox web interface does not show Keel templates. Use keel-pve, or download the file from the mirror. The commands are the same as on the page of each application.

With keel-pve

keel-pve gets the signed index of the Keel templates and checks the template against it. Install keel-pve from the Keel archive, suite trixie-testing. Then run these commands on the Proxmox node:

# example: Keel LNMP. Change keel-lnmp for another application.
keel-pve update
keel-pve download local keel-lnmp

With the file

  1. Download the template, its .sha512 and its .sha512.asc from the mirror.
  2. Check the signature.
  3. Check the digest.
  4. Copy the template to /var/lib/vz/template/cache/ on the Proxmox node.
  5. Make the container.
# example: Keel LNMP 19.0-6. Change the names for another image.
M=https://mirror.keellinux.org/images
F=debian-13-keel-lnmp_19.0-6_amd64.tar.zst
curl -fLO $M/$F -O $M/$F.sha512 -O $M/$F.sha512.asc
curl -fLO https://archive.keellinux.org/keel-images-keyring.asc

sqv --keyring keel-images-keyring.asc $F.sha512.asc $F.sha512
sha512sum -c $F.sha512

cp $F /var/lib/vz/template/cache/
pct create 200 local:vztmpl/$F --hostname lnmp \
  --unprivileged 1 --features nesting=1 \
  --net0 name=eth0,bridge=vmbr0,ip6=auto

The .sha512.asc file holds two signatures: one by the archive key and one by the images key. The command uses the images keyring, so sqv prints "Missing key" for the archive key. This is expected. If sqv prints the fingerprint E71DB9C3CA6AC18075395CC3ED3A709C4F3E2F3C, the signature is good.

Start the container and log in on its console as root. The first boot asks its questions there.

The ISO has the same 3 files: change .tar.zst to .iso in the names. Boot the machine from the ISO and install. The first boot of the installed system asks the same questions as the template.

Cloud simple needs 2 nodes of the same appliance. Cloud advanced needs 2 data nodes and a witness. The page of each application has a guide for each mode, with one column for each node. The cloud page describes the modes.
